# 反滥用：限流与机器人防护（#27）

公开写面的滥用控制。老系统的对应物是 FEAT-019（DB 限流 + IP 黑名单 +
honeypot/reCAPTCHA），其「进程内存 Map 限流器」被老仓库自己的安全架构文档
列为明确不继承的形态——本仓库从第一行起就是 PG 存储。

设计依据：#232 §1.1「防滥用：公开接口统一限流、honeypot、reCAPTCHA」。

## 限流内核（切片 1）

### 形状

- **固定窗口计数，状态在 PG**：`rate_limit_counters` 一行 =
  (标识类型, 标识, 动作, 窗口起点)。递增与判定是同一条
  `INSERT … ON CONFLICT DO UPDATE … RETURNING`——同窗口并发写撞主键串行化，
  多个 API 实例共享同一张表，「多实例下限流仍然准确」（验收第 1 条）是结构
  保证而不是部署纪律。
- **中间件**：`authRateLimitMiddleware`（`apps/api/src/security/rate-limit.ts`）
  挂在 `/api/auth/*` 会话门之前。规则册（`AUTH_RATE_LIMIT_RULES`）按路径前缀
  分动作：

  | 动作 | 面 | 阈值 |
  | --- | --- | --- |
  | `auth.sign-in` | 密码/社交登录 | 30 次 / 5 分钟 / IP |
  | `auth.sign-up` | 注册 | 10 次 / 小时 / IP |
  | `auth.password-reset` | 忘记密码 + 重置 | 10 次 / 小时 / IP |
  | `auth.two-factor` | TOTP 等第二因子验证 | 10 次 / 5 分钟 / IP |
  | `auth.other` | 其余 /api/auth/* POST（背底） | 300 次 / 5 分钟 / IP |

  阈值是代码常量（与审批催办 24h 节奏同一裁法）：第一个要调的消费域把它抬
  进配置面。GET 不限（认证面的 GET 是令牌消费与状态读，不是可暴力面）。
  Stripe/PayPal webhook 不在册：来源是服务商基础设施、验签即认证，按 IP 限
  只会拦到它们自己。

### 裁决（与老系统 FEAT-019 的同与不同）

1. **来源头信任规则原样继承**：`cf-connecting-ip` → `x-forwarded-for` 的
   **最后一个**元素（每个代理把对端追加在尾部，头部是客户端可自填的）→ 都
   没有则不可归因。标识原样存储、截断 100 字符，不归一化（等真实样本）。
2. **不可归因 → 不计数（fail open）**：老 `consume_rate_limit` 对 null 标识
   的原裁决。共享「unknown」桶等于让同一出口背后的无辜用户互相锁死；正常
   部署拓扑下（ALB/Cloudflare）来源头总在，这条路径出现说明部署头配置断了
   ——那是部署要修的事，不该由 429 来暴露。debug 日志留了诊断入口。
3. **拒绝照计数**（与老系统刻意相反）：老的限流器住在业务事务里，拒绝时
   事务回滚把增量也吃了，计数器停在阈值上；新的计数自成一笔，超限请求继续
   累计——窗口内真实到达量诚实可查，`denied` 行的 `count_at_denial` 与计数
   器一致可对账。
4. **拒绝有台账**（老系统做不到的）：`rate_limit_denials` 一行 = 一次拒绝的
   事实（标识、动作、窗口内第几次、当时阈值、request_id）。老的拒绝记录随
   事务回滚蒸发，只剩一条 warning 日志；app 层限流器写记录自成一笔，验收
   第 3 条「管理页面能查看被拦截的请求」有了数据面（页面待做）。台账写失败
   只告警不改判：429 的权威在计数器，台账是遥测不是闸门。
5. **限流器错误不静默吞**：计数器查询失败让异常冒泡（onError 兜 500）——
   认证端点本来就依赖同一数据库，装作「没限制住」才是谎报；这不制造新的
   可用性悬崖。
6. **429 响应不携带策略细节**：body 只有 `{"error":"rate_limited"}` +
   标准 `Retry-After`（窗口剩余秒数）。拒绝面向攻击者确认的只有「慢一点」，
   具体阈值在文档与代码里。

### Better Auth 自带限流的关系

Better Auth 生产模式自带进程内限流（默认 100 req/60s/IP），保留不动：它是
单实例第一道，本切片的 PG 层是跨实例、可持久记账的第二道。两层阈值独立，
先撞哪层答哪层的错。

## 拦截可见面（切片 2）

验收第 3 条「管理页面能查看被拦截的请求」的落点。API 两读
（`apps/api/src/routes/rate-limit-denials.ts`，`audit.read` 权限点门，与审计
日志、错误事件同一扇门）+ web 一页（`/system/rate-limits`）：

- **台账列表** `GET /api/rate-limit-denials`：最新在前 + 精确 total（分页
  与 audit-events 同裁）；`action` / `identifier` 精确匹配过滤（对账读法，
  不做模糊搜索）。
- **动作汇总** `GET /api/rate-limit-denials/summary`：默认 7 天窗口按动作
  分组——次数、distinct 来源数（区分「一个人手滑」与「一个网段在扫」）、
  最近一次拒绝时刻。分诊的第一屏，与 error-events 的指纹汇总同形。
- **页面无动词**：台账是遥测不是闸门——429 的权威在计数器，页面只回答
  「谁在撞、撞什么、撞多狠」；解禁/拉黑是 IP 黑名单切片的事，那里等真实
  滥用场景定治理面。

## 清理任务

`rate-limit-cleanup`（worker，每 10 分钟）：计数器行保留 1 天（窗口最长
1 小时，兜住未来更长窗口的规则）、拒绝台账保留 30 天（安全遥测，回溯排查
以周计；台账不是审计，不是合规记录）。老系统任务表 A22
`platform-rate-limits-cleanup` 的后继，见 docs/cron-migration.md。

## 新面接入清单

新的公开写面（询价向导、门户表单、webhook 接收器…）接入限流：

1. 在 `AUTH_RATE_LIMIT_RULES`（或新表面自己的规则册）加一行：动作名、阈值、
   窗口、路径前缀；
2. 挂 `authRateLimitMiddleware`（或组合 `consumeRateLimit` 自定义键）；
3. 表单面同时接 honeypot（该切片进场时补 here 链接）；
4. 集成测试至少一条「超限即 429」。

机器人检测（honeypot / reCAPTCHA v3）随第一个公开表单域一起落：没有表单
面时它们没有消费方，先建机制是空转。
