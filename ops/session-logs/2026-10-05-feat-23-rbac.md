## 判断层(手写 —— hook 写不出这部分)

**做了什么判断,为什么:**

1. **设计权威取 #232 §12,不照搬老 `core.app_role` 的 16 个值。** 老枚举
   (super_admin/ceo/coo/cmo/account_executive/closer/ops…)是 FEAT-001 时代的
   产物,#232 §12 明文收敛为 14 员工角色+客户门户,并裁定「标签设计是权限点
   不新增角色」。issue 正文里引用的 `useAdminPermissions.tsx`、`ops_roles`、
   `ROLE_EDITABLE_PHASES` 在老检出里**不存在**(grep 全仓库为空)——与 #22
   切片 1 的调研结论一致,那些属于更老的 ally-nutra/ops 仓库,不追。老→新
   角色映射写成「建议表」放进 docs,标注「迁移执行时由 owner 逐条确认」,
   不在本切片假装是裁定。

2. **角色用 PG 枚举(闭集)、权限点用 text+代码注册表(开集)。** 角色变更
   (#232 裁定 14 个不变、R-16-4)应当走 migration 有迹可查;权限点随业务
   模块持续增加,每次都动数据库不值得,合法性由 `PERMISSIONS` 注册表 +
   zod 收口。老系统 `core.user_roles.scope`(租户预留列)不迁:#232 没有
   租户级角色,预留列搬过来是死 schema。

3. **R-16-6(授予 owner/admin/finance 需老板确认)的落地方式:fail-closed
   的中间态。** 审批流(#221)还不存在,真流程做不了;放任 admin 可授 owner
   等于开门。裁定:这三类授予/撤销(撤销同门,撤比授更敏感)只允许 owner
   角色本人执行,403 `owner_approval_required`,doc 写明这是 #221 前的
   等价物。引导问题(第一台机器没有 owner)由 `grant-role.ts` CLI 解,
   绕过 API 门但写审计(actor `cli:grant-role`)——运维动作显性化。

4. **验收第 2 条「缺失时 lint/测试会报错」的实现:声明清单 + 双向比对测试。**
   Hono 的 app.routes 把 `app.use` 中间件挂载也列为 method=ALL 条目、且中间件
   编译进 handler 链后无法反射检查,「lint 插件」路线不现实。改为
   `routes/registry.ts` 单一清单(app.routes ↔ API_ROUTES 双向比对,公开路由
   集合钉死)+ `kind:"permission"` 路由必须配集成 403 测试的纪律。诚实边界:
   测试能逼「每条路由有声明」,不能机械证明「声明与中间件一致」——那层靠
   PR review,doc 里写明。

5. **审计只记真实变更。** `grantRole`/`revokeRole` 返回 boolean
   (onConflictDoNothing/returning 判定),重复授予答 200 `granted:false`
   且不写审计行——审计是「发生了什么」的记录,不是「谁调过接口」的日志。
   `user_permission` 表本切片建好并参与生效权限计算,但 HTTP 管理端点
   不开(没有需要它的模块),label_design 的授予端点随 #169 进场——
   避免「能授权限点却没有任何路由消费它」的死接口。
