## 判断层(手写 —— hook 写不出这部分)

**做了什么判断,为什么:**

1. **验收第 1 条裁定为「做不成」,没有做导入脚本。** issue 要求「已绑定 2FA
   的管理员迁移后无需重新绑定」并「评估 Better Auth two-factor 插件能否直接
   导入现有密钥」。对着 dist 源码把评估做穿:`@better-auth/utils` 的 HMAC
   `importKey("raw", TextEncoder(key))` —— better-auth 全程拿**存储字符串的
   UTF-8 字节**当 HMAC 密钥,createOTP 不解释 base32;而老系统 GoTrue
   (pquerna/otp)的密钥是 20 随机字节的 base32 编码,真身是任意二进制。
   TextEncoder 对非 ASCII 必损,所以「既能存进 better-auth、UTF-8 字节又等于
   老认证器持有的那些字节」的字符串不存在。备份码那边是 bcrypt 单向哈希对
   「整批明文 JSON 的加密体」,同样无路。评估的关键产出是**不做**的裁定:
   把 base32 串原样写入会造出「密钥存进去了、老认证器永远对不上码」的死行,
   管理员密码过了、挑战卡死——比明说「要重绑一次」更糟。导入脚本因此不落地,
   迁移路径 = 强制门引导 + /settings/two-factor 自助重绑,评估全文在
   docs/auth.md 与 PR。验收第 1 条按此修订,PR 里明说。

2. **强制门选「authz 后置中间件」而非登录拦截。** #232 §12 只说管理员强制,
   没说不让登录。登录时拦死的话,未绑定的管理员连 /two-factor/enable 都够
   不着(绑定需要会话)。后置门(admin 无 2FA → 业务路由 403
   two_factor_required;/api/me 豁免;/api/auth/* 本就在门之前分流)让绑定
   流程自洽、关闭 2FA 后立即回到门后(自愈)、且此后注册的业务路由默认在门
   后——新模块忘接门也不开口子(fail closed)。

3. **强制集合只有 admin,owner 没进。** 设计原文「管理员和有电子签名权限的
   人」;owner(老板)是另一个角色,设计未列。顺手把老板拉进强制名单是安全
   直觉,但那是设计裁决的修订——做成一行常量(TWO_FACTOR_ENFORCED_ROLES +
   注释),要改是一分钟的事,不该由实现顺手决定。e-sig 权限点(#219)落地时
   加进集合即可,注释已写明。

4. **备份码语义换成通行语义,不渡河老系统。** 老系统 FEAT-019 p6:备份码 =
   恢复机制(消费即删因子、强制重绑),因为它要守 GoTrue 的 aal 语义。
   better-auth 的备份码 = 第二因子(丢设备顶替登录、用一次少一个)。老语义
   的存在理由(aal)在新系统不存在,且「删因子迫使重绑」对用户更狠;新语义
   是通行做法,测试钉住「用过的码失效、没用过的仍可用」。

5. **测试用 better-auth 自己的 TOTP 实现生成码,不引第二套。**
   `auth.api.generateTOTP({body:{secret}})` 是 server-only 端点,正好当测试
   器具。第一轮全红的根因也因此暴露:我最初从 otpauth URI 取 base32 密钥喂
   给它——createOTP 用原始字符串做 HMAC,URI 里的 base32 只是认证器的传输
   编码。测试改为从库里解密(顺带钉住「密文可用我们的 env 密钥解开」这个
   真实性质),等价于真实认证器持有的密钥。

6. **#23 的 user-roles 测试适配强制门:置位前先签出会话。** admin 夹具直接
   DB 置位 two_factor_enabled(RBAC 测试不走绑定仪式),但置位后登录响应是
   挑战、不再发会话 cookie,原 cookieFor 每次现签登录拿到的全是过期空
   cookie(401)。修法:fixture 里置位**前**签出 admin 会话、cookieFor 记忆
   各 actor——直接置位不吊销既有会话,行为正确且改动最小。

7. **web 侧响应类型没建模 twoFactorRedirect,zod 收窄而不是断言。**
   better-auth 1.7.7 的 sign-in/email 推断类型不含插件改写的形状(runtime
   有、类型没有;type-probe 证实)。仓库纪律是外部输入一律 zod,照办:
   `z.object({twoFactorRedirect: z.literal(true)}).safeParse(data).success`。

8. **QR 用 uqr(零依赖、3KB),不手搓不引重依赖。** 老系统渲染 supabase-js
   返回的 QR SVG;新系统 better-auth 只给 otpauth URI,uqr 在浏览器端本地
   渲染,手动输入密钥同屏兜底(老系统同款)。

**踩的坑:**

- **「验证成功即换发会话」**:verify-totp 完成绑定时 better-auth 会新建
  会话、**当场删除旧会话**。enrollTotp 帮手第一版返回的是 enable 时那个
  cookie,后续所有 disable/regenerate 测试 401——返回值必须取 verify 响应
  的 Set-Cookie。同类:挑战登录的响应里有一条**用于清除旧 cookie 的过期空**
  session cookie,断言「没发会话」时得排除它。
- **批量 python 替换改坏了测试的解构**:`enrollTotp(email)` 全局替换成
  `enrollTotp(userId, email)` 时,只解构了 email 的调用点引用了不存在的
  userId——四个用例 ReferenceError。机械替换要跟着变量声明走。
- **GoTrue 密钥格式的两次自我纠偏**:先以为「老系统 admin-2fa 手搓 TOTP」
  (issue 的老系统现状描述),security-architecture.md 指出那套已被 GoTrue
  原生 MFA 替换(明文密钥是审计点名缺陷);再以为「拿到 base32 密钥就能导」,
  HMAC 源码读穿后才定案「二进制真身、导不了」。结论换了两次,证据都在
  docs/auth.md 里留了痕。
- **lru 探针文件污染 lint**:验证 uqr 用的临时 .mjs 落在仓库根,eslint 按
  allowDefaultProject 报错——临时文件要么进 gitignore 目录要么当场删。

**值得纳入项目的点:**

- 「读依赖 dist 源码定合同」第七、八次命中:sensitiveSessionMiddleware、
  secretConfig=secret(字符串)、换发会话删旧会话、TextEncoder HMAC——四个
  行为全部只看文档/类型看不出来,其中两个(换发、TextEncoder)直接改写了
  测试写法。
- 「集成测试必须覆盖 Set-Cookie 的全生命周期」:better-auth 一条请求可能

  都要按值区分,不能数条数。
