## 判断层(手写)

### 本次的关键判断

1. **切片边界:服务端内核先行,前端组件随首个消费域**。#219 五个要点里四个
   是服务端(重输密码、含义、锁定、审计绑定、离线同步),「统一的签名组件」
   在没有可签名记录、没有消费页面的今天只能是没有调用方的死 UI;注册表为空时
   连组件的成功路径都调不出来。裁:本切片交付签名内核 + API + 四条验收的
   接口测试,组件随 #221(审批)或 #204(批次放行)的第一个真实签署场景
   落地,PR 写 Part of #219 列明剩余。
2. **可签名注册表刻意为空 + tasks 锁定检查预埋**。老系统没有对应物,批记录/
   检验/放行等受监管记录全在 phase-3/4——现在没有任何一条业务记录该被签,
   把 task 注册成可签名 = 发明无需求的产品行为。裁:注册表空、
   `registerSignableSubject` 是属主域的唯一接缝(与 subjects/registry.ts 的
   可见性门并存:看得到才签得到);但 tasks PATCH 已预埋 `isSubjectSigned`
   检查(空表上一次廉价 exists 查询,恒通过),首个域注册那天锁定即生效,
   「已签名记录的修改请求被服务端拒绝」在路由层是活的契约,由集成测试用
   夹具域(走生产注册接缝)证明。
3. **recordVersion + recordHash 双绑定**。「关联到被签记录的具体版本」不能
   只存个版本号字符串(可否认),也不能存全文快照(膨胀且属主域各异)。裁:
   属主域 load 给「版本标 + 内容快照」,内核对
   `{subjectType, subjectId, version, snapshot}` 的规范化 JSON(canonicalJson
   键全序,序列化顺序不影响哈希)取 SHA-256 落列——事后任意时刻可重算比对,
   内容被改写立即现形(Part 11.70 签名-记录联结的结构化落点)。
4. **signedAt/receivedAt 分列,在线/离线同一条 POST**。离线补同步不是新端点:
   客户端永远生成 clientToken(幂等键)+ 可选 signedAt;服务端只拒绝「明显
   在未来」(5 分钟设备时钟容差),离线多久都收——原签名时间是事实,联网晚
   不是它的错。重放(同 token)返回原行 200 且不落第二行审计;token 串用
   (字段对不上)按 already_signed 拒绝。receivedAt = 服务端收 moment,
   两列之差就是离线窗口,审计行两个时间都带。
5. **签名仪式的检查顺序**:2FA(403)→ 可见性(400/404)→ 可签名(400)→
   **密码(401)→ clientToken 重放 → 一人一号(409)**。密码放在所有业务
   状态判定之前:未通过重认证的调用方不该从本端点探到「这条记录是否已被
   签过」;2FA 放最前:未启用双因素的用户连记录存在性都不该探到(#24 强制门
   管常规路由,签名仪式这里再收一道,无例外开关)。
6. **signerId 外键不带 CASCADE**(与 comments/follows 的「社交内容共生灭」
   刻意相反):签名是监管记录,挂着签名的账号行删不掉(PG 默认 NO ACTION);
   0012 触发器把签名行本身做成 append-only——「发生过的事实」改写/抹掉都
   不存在合法业务路径,更正走新记录或变更流程(#219 正文原句)。
7. **密码重验复用 #22 切片 5 的哈希分派**:verifySignerPassword 查 credential
   account 行走 verifyLegacyPassword(bcrypt/scrypt 格式分派)——签名与登录
   是同一套口令真相,不出现「能登录不能签」的第二套哈希语义;导入的 bcrypt
   老用户原密码即可签。

### 踩的坑(都花时间修了)
